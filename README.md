# screenshare

Браузерная комната для совместного созвона с шарингом экрана, без регистрации и записи. Транспортно все участники равноправны (mesh), но один из них — лидер, у которого есть права модерации (настройки комнаты, лобби, см. «Права и лидер»); шарить экран в моменте может только один. Плюс текстовый чат комнаты (идёт напрямую между участниками, сервер его не хранит) и микрофон каждого участника.

## Архитектура

- **Симметричная mesh-комната с лидером, протокол v4.** Никакого выделенного «вещающего» в смысле медиа — все участники комнаты соединяются между собой mesh: у каждого участника по одному прямому `RTCPeerConnection` с каждым другим участником комнаты, а поверх него — DataChannel-шина (см. ниже), которую использует чат. Один из участников при этом — лидер (роль сигналинга/модерации, не медиа): назначается автоматически (создатель через `leaderToken` или первый вошедший) и может менять права гостей и настраивать лобби (см. «Права и лидер»).
- **Шаринг экрана — временное состояние комнаты, а не роль.** Начать шарить `getDisplayMedia()` может любой участник кнопкой в интерфейсе, но одновременно — только один; пока экран занят, остальным приходит отказ, и они могут захватить его сразу после того, как текущий владелец остановит показ или отключится.
- Мобильные браузеры (Android Chrome, iOS Safari) не реализуют `getDisplayMedia` — на них веб-шаринга экрана нет в принципе, поэтому кнопка «Экран» на таких устройствах в интерфейсе не показывается вовсе (фронтенд детектит поддержку и прячет кнопку, см. `static/room.js`).
- **Видео и аудио идут напрямую между браузерами** по WebRTC (mesh P2P). Через backend медиатрафик не проходит ни байтом.
- Весь WebRTC (`getDisplayMedia`, `getUserMedia`, `createOffer`/`createAnswer`, ICE) — на фронтенде, на чистом JS. На Rust WebRTC-стек не используется.
- Backend (Rust/axum) делает ровно четыре вещи:
  1. `POST /api/rooms` — создаёт пустую комнату и отдаёт `roomId` + одноразовый `leaderToken` для URL;
  2. signaling-релей поверх WebSocket (`/ws`) — вход в комнату (включая лидерство и лобби), пересылка offer/answer/ICE-кандидатов между любой парой участников, чат комнаты, заявки на шаринг экрана, смена настроек комнаты лидером;
  3. раздача статики фронтенда;
  4. `GET /qr.svg?room=<roomId>` — QR-код на короткую ссылку комнаты.
- Состояние комнат (участники, каналы для рассылки, кто сейчас шарит экран) — **целиком в памяти процесса** (`HashMap`). Содержимого чата среди него нет вовсе — сервер его не хранит, см. раздел «Приватность» ниже.
- Лимит: **максимум 6 участников** в комнате одновременно; 7-й получает отказ `room-full`.
- Комната живёт, пока в ней есть хоть один участник. Пустая комната (только что создана — никто ещё не подключился, либо все вышли) не удаляется сразу: она живёт `EMPTY_ROOM_TTL_SECONDS` (по умолчанию 120с — время создателю перейти по ссылке), и удаляется фоновым реапером, только если за это время никто не подключился/не переподключился.
- Серверный ping/pong-хартбит: раз в 20с сервер шлёт `Ping`, и если два подряд остаются без ответа — соединение считается мёртвым и закрывается (иначе тихий обрыв без FIN ловится только TCP-таймаутом ОС, это минуты).
- Чат идёт напрямую между участниками по mesh RTCDataChannel (см. «Шина комнаты» ниже) — сервер контента не видит и не хранит вообще. Клиентский rate-limit (мягкий, не чаще 10 сообщений за 10с) блокирует отправку в панели; отдельный серверный rate-limit (те же 10/10с) защищает только адресный fallback-путь — на случай, если DataChannel-шина до конкретного пира ещё не открыта.
- **Шина комнаты (mesh RTCDataChannel).** У каждой пары участников, помимо медиа-`RTCPeerConnection`, есть свой `RTCDataChannel` («bus») — заводит его impolite-сторона (см. polite/impolite выше) обычным `createDataChannel`, polite получает свою половину через `ondatachannel`; открывается сразу при входе в комнату, ещё до включения любой медиа. Чат (Ф1) — первый потребитель шины: сообщения (конверт `{v, id, lamport, from, name, kind, text, replyTo, ts}`, расширяемый под будущие реакции/реплаи/файлы) рассылаются broadcast всем пирам с открытым каналом; пирам без открытого канала — адресный fallback через сервер (см. WebSocket-протокол ниже). Порядок ленты — по (lamport, from), одинаковый у всех независимо от порядка доставки по сети; дедуп по id. История — буфер последних 50 сообщений в памяти вкладки (не персистентно), новичок при входе запрашивает её у первого пира из `joined.peers` по той же шине.
- STUN — публичный `stun:stun.l.google.com:19302`. TURN — опциональный, отдельный сервер (например `turn-rs`), настраивается через переменные окружения.

## Права и лидер

Комната имеет ровно одного **лидера** и (опционально) обычных участников-гостей. Членство и роль — целиком серверная истина (никакого кворума или голосования не нужно: сервер сам знает, кто есть кто и когда кто вошёл).

- **Кто становится лидером.** `POST /api/rooms` теперь возвращает `{roomId, leaderToken}` — одноразовый токен. Создатель комнаты предъявляет его в своём `join-room` (`leaderToken`), и если он совпал с хранимым в комнате — становится лидером, а токен тут же сгорает (второе предъявление того же токена уже ничего не даёт — в комнате уже есть лидер). Если токен никто не предъявил, а лидера в комнате ещё нет (совсем свежая комната, либо восстановленная после рестарта через `PUT /api/rooms/{id}`, который токен вообще не выдаёт) — лидером становится первый вошедший, как есть.
- **Смена лидера.** Когда лидер выходит (явный `leave`, закрытие вкладки, обрыв соединения), сервер, если в комнате остались другие участники, детерминированно назначает нового лидера — того, кто подключился раньше всех остальных (`joined_at` каждого участника сравнивается на сервере). Кворум и голосование не нужны — участники комнаты сами по себе не переизбирают лидера, это решает исключительно сервер по одному строгому правилу, и результат у всех одинаковый. Уходя, лидер оставляет и свои непринятые заявки лобби (см. ниже) — они переезжают к новому лидеру.
- **Переподключение с прежним peerId.** Если сервер ещё не успел вычеркнуть участника из комнаты (быстрый реконнект), лидерство при возврате сохраняется как было. Если же сервер уже удалил его и успел назначить нового лидера — вернувшийся входит обычным гостем, лидером он больше не является (несмотря на тот же `peerId`).
- **Настройки комнаты** (`Room.settings`, меняет только лидер через `update-settings`, применяются целиком): `lobbyEnabled` (комната ожидания, по умолчанию `false`), `guestChat`/`guestAudio`/`guestVideo`/`guestScreen` (права гостей на соответствующие возможности, по умолчанию все `true`). Изменение рассылается всем участникам как `settings-changed`.
- **Лобби (wait room).** Пока `lobbyEnabled=true`, любой НЕ-лидер при входе не становится участником сразу: сервер кладёт его в отдельный список ожидающих (не в число участников — лимит 6 участников их не касается, но самих ожидающих не больше 10 одновременно), шлёт ему `waiting`, а лидеру — `join-request {peerId, name}`. Лидер решает `approve {peerId}` (ожидающий становится полноценным участником — ему `joined`, остальным `peer-joined`) или `reject {peerId}` (ожидающему `join-rejected`, сервер сам закрывает его сокет). Если ожидающий отвалился сам, не дождавшись решения — лидеру `join-request-cancelled`. Если лидер сменился, пока заявки ещё висели — новый лидер получает их все заново (`join-request` за каждую). Если комната опустела целиком (даже с живыми заявками в лобби) — все ожидающие получают `join-rejected` и отключаются, а сама комната уходит в обычный TTL пустой комнаты.
- **Права гостей и как они реально проверяются:**
  - **Шаринг экрана** — серверу видно и подконтрольно полностью (это состояние комнаты, не P2P-поток): при `guestScreen=false` `share-start` гостя получает `share-rejected` с `reason: "forbidden"` (без `busyPeerId` — это не конфликт из-за занятости, а отказ по правам); лидеру можно всегда. Если у гостя ОТОБРАЛИ право прямо во время его шаринга — сервер сам обрывает: `share-stopped` всем, не дожидаясь действий гостя.
  - **Чат** — сервер контролирует только свой адресный fallback-релей (см. «Шина комнаты» выше): при `guestChat=false` гостю в ответ на `chat` приходит `error`; лидеру можно всегда. Основной путь чата (mesh RTCDataChannel напрямую между браузерами) сервер физически не видит — честно говоря, технически мотивированный гость может продолжить слать сообщения по DataChannel в обход этого запрета, сервер тут бессилен в принципе (см. «Приватность» — сервер и не хранит, и не может блокировать P2P-канал, до которого у него нет доступа).
  - **Аудио и видео** — сервер вообще не участвует в медиапотоках (чистый mesh P2P, см. «Архитектура» выше) и физически не может ни разрешить, ни запретить их на уровне транспорта. `guestAudio`/`guestVideo` — это входные данные для фронтенда: сервер лишь хранит и рассылает значение настройки (`settings-changed`), а получатели медиапотока сами решают, воспроизводить ли трек от участника, которому лидер отключил аудио/видео (условно говоря, контроль на стороне клиентов-получателей, а не отправителя и не сервера).

## Приватность

Сервер спроектирован так, чтобы после завершения сессии от неё не оставалось никаких следов:

- **Никакой БД и никакого хранения на диске.** Ни SQLite, ни любого другого хранилища в проекте нет. Состояние комнаты (участники, имена, кто шарит экран) живёт только в памяти процесса.
- **Содержимое чата сервер не видит и не хранит вообще.** Чат идёт напрямую между участниками по mesh RTCDataChannel (см. «Шина комнаты» выше) — сервер в этом пути не участвует. Единственное исключение — адресный fallback-релей на случай, когда DataChannel-шина до конкретного пира ещё не открыта: сервер лишь пересылает опаковый JSON-конверт (как `sdp`/`candidate`) от отправителя адресату, не разбирая и не сохраняя ни байта; в памяти комнаты для чата вообще нет ни поля, ни буфера. История чата (последние 50 сообщений) живёт только в памяти вкладки каждого участника и пропадает при закрытии/обновлении страницы.
- **Комната умирает — умирает вся её память.** Как только комната удаляется (реапер по истечении `EMPTY_ROOM_TTL_SECONDS` пустоты) или процесс перезапускается — имена участников исчезают безвозвратно, восстановить их неоткуда.
- **IP-адреса и порты клиентов нигде не логируются и не хранятся.** В tracing-логах фигурируют только `room`/`peer` идентификаторы (см. `src/ws.rs`, `src/state.rs`) — никакого сетевого адреса участника сервер не записывает и не сохраняет.
- Медиатрафик (видео/аудио) и чат через backend не проходят вообще (кроме редкого адресного fallback-релея чата выше) — прямой P2P WebRTC между браузерами.

## Запуск

```
cargo run
```

По умолчанию сервер слушает порт `3000`. Открыть в браузере: http://localhost:3000

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PORT` | нет (по умолчанию `3000`) | порт HTTP/WebSocket-сервера |
| `EMPTY_ROOM_TTL_SECONDS` | нет (по умолчанию `120`) | сколько секунд живёт пустая комната (никто не подключился или все вышли), прежде чем фоновый реапер её удалит |
| `STATIC_DIR` | нет (по умолчанию каталог `static/` рядом с `Cargo.toml`) | откуда раздавать статику фронтенда; в контейнере — например `/app/static` |
| `TURN_URL` | нет | адрес TURN-сервера (например `turn:example.com:3478`) |
| `TURN_USERNAME` | нет | логин для TURN |
| `TURN_PASSWORD` | нет | пароль для TURN |

Если `TURN_URL` не задан, клиент получает от `/config` только STUN-сервер Google. TURN нужен, если P2P-соединение не устанавливается напрямую (симметричный NAT и т.п.).

## Проверка локально в двух вкладках

`localhost` браузер считает secure context, поэтому `getDisplayMedia()` работает без HTTPS.

1. `cargo run`.
2. Вкладка 1: открыть http://localhost:3000, нажать «Создать комнату» — URL комнаты вида `http://localhost:3000/r/<roomId>` создаётся сразу (`POST /api/rooms`) и открывается тут же.
3. Скопировать ссылку и открыть её в вкладке 2 (или другое устройство в той же сети, если сервер слушает `0.0.0.0`) — оба участника видят и слышат друг друга по прямому WebRTC-соединению.
4. Поделиться экраном кнопкой может начать ЛЮБОЙ участник; пока экран занят одним, у остальных попытка захвата отклоняется — начать может кто-то другой только после того, как текущий владелец остановит показ или выйдет из комнаты.
5. Можно открыть ссылку ещё в нескольких вкладках, до 6 участников одновременно.

## Тестирование

Два независимых уровня, друг от друга не зависят.

### 1. Протокол сигналинга (без браузера)

```
node tests/signaling.test.mjs
```

Чистый Node (>= 22, без npm-зависимостей): сам собирает `cargo build`, поднимает
`./target/debug/screenshare` на порту 3311 и гоняет полный жизненный цикл
комнаты/чата напрямую по WebSocket (`ws://`/`fetch`), без браузера. Сервер
полностью эфемерен (см. «Приватность») — тест это тоже проверяет (после
прогона в рабочем каталоге не остаётся файлов БД). Гарантированно убивает
сервер(ы) за собой.

### 2. Браузерный e2e (реальный Chrome, реальный WebRTC-поток и чат)

```
cd tests/e2e && npm install && node basic.spec.mjs
```

Требуется установленный локально Google Chrome. `tests/e2e/` — отдельный
дев-инструментарий со своим `package.json` (единственная зависимость —
`playwright-core`; браузеры этот пакет не скачивает, тест использует
системный Chrome через `channel: 'chrome'`).

Сценарий: собирает и поднимает сервер на порту 3322,
открывает вещающего и двух зрителей в реальном Chrome, проверяет, что видео
реально идёт (`videoWidth`/`readyState`/растущий `currentTime`), чат работает
между всеми тремя участниками (включая бейдж непрочитанных у свёрнутой по
умолчанию панели), счётчик зрителей показывает 2, а закрытие вкладки
вещающего показывает зрителям оверлей «Трансляция завершена». Отдельно
проверяется, что чат (Ф1) действительно идёт по mesh RTCDataChannel, а не
через сервер: шпион на `WebSocket.send` каждой страницы (см.
`installChatWsSpy` в `basic.spec.mjs`) доказывает, что при живом
установившемся mesh ни один `chat`-фрейм не уходит в серверный сокет ни у
кого из троих участников; плюс кейс истории — третий участник входит в
комнату уже ПОСЛЕ того, как между первыми двумя было отправлено два
сообщения, и видит оба, получив их по DataChannel от пира (не от сервера —
серверной истории чата больше нет, см. «Приватность»).

Про диалог `getDisplayMedia()` в автоматизации: реальный захват экрана в
Chrome требует либо клика пользователя в системном пикере, либо флагов вида
`--auto-select-desktop-capture-source=<имя источника>` и
`--use-fake-ui-for-media-stream`/`--use-fake-device-for-media-stream`. На
macOS это дополнительно упирается в системное разрешение «Screen Recording»
(TCC), которое нельзя выдать неинтерактивно — если оно не выдано, промис
`getDisplayMedia()` в headless/автоматизированном Chrome может зависать
надолго или навсегда независимо от флагов; зависший запрос вдобавок тормозит
последующие медиа-операции той же страницы. Поэтому по умолчанию тест на
уровне арнесса (не трогая `static/`) сразу подменяет `getDisplayMedia` на
синтетический источник (`canvas.captureStream()`), а `getUserMedia` микрофона —
на осциллятор Web Audio; WebRTC-транспорт при этом проверяется по-настоящему.
Попытки реального захвата включаются переменными `E2E_TRY_REAL_CAPTURE=1` и
`E2E_TRY_REAL_MIC=1` (полезно на машинах, где флаги и разрешения работают);
использованный источник явно помечается в выводе теста.

Переиспользуемая инфраструктура обоих браузерных тестов (мини-раннер,
сервер, медиастабы, чат-хелперы) вынесена в `tests/e2e/helpers.mjs`.

### 3. Браузерный e2e устойчивости к обрывам (`resilience.spec.mjs`)

```
cd tests/e2e && node resilience.spec.mjs
```

Отдельный сервер на порту 3333. Сценарии: обрыв вкладки зрителя с включённым
микрофоном (счётчики и индикаторы гаснут у остальных, чат не рвётся),
`page.reload()` посреди шаринга экрана (переподключение, старый шаринг
корректно освобождён; история чата у переподключившегося пуста — Ф1 не
хранит её на сервере, а к этому моменту сценария участник в комнате уже
один, спросить не у кого — реальный кейс получения истории от живого пира
по DataChannel покрыт в `basic.spec.mjs`), потеря сети у зрителя
(`browserContext.setOffline(true)` — эмпирически в данной среде не рвёт уже
открытый WebSocket мгновенно, см. комментарий в файле), переполнение
комнаты (6-й зритель получает «Комната заполнена»), и клиентский (Ф1,
мягкий) rate-limit чата: 11-е сообщение подряд блокируется в панели
отправителя с сообщением об ошибке, остальные 10 доходят до собеседника.

Отдельный сценарий — рестарт сервера (см. «Живучесть звонка при деплое»):
3 участника (у одного микрофон, у другого активный шаринг экрана, есть
переписка) → сервер целиком останавливается и поднимается заново на том же
порту (`server.stop()` + `server.start()`) → проверяется, что баннер
«Переподключение…» появляется и исчезает, тайлы/счётчик участников
восстанавливаются, P2P-чат и его история (клиентские буферы) не пострадали,
видео продолжает идти, а шаринг экрана либо переигрывается автоматически,
либо — если это оказалось невозможно — честно уходит (тест логирует, какой
из двух исходов случился по факту).

## TURN-сервер (turn-rs) рядом, кратко

Если STUN недостаточно (P2P не устанавливается за NAT), рядом поднимается `turn-rs`.

Docker:
```
docker run -d --network=host ghcr.io/webrtc-rs/turn-server \
  --public-ip <внешний-IP> --listening-port 3478 \
  --realm example.com --users "user=pass"
```

Или `cargo install turn-server` и запуск с теми же флагами (см. `--help`).

Приложению после этого выставить:
```
TURN_URL=turn:<внешний-IP>:3478
TURN_USERNAME=user
TURN_PASSWORD=pass
```

## Деплой

Прод крутится в KubeSolo (single-node k8s) на `chat.fedorov.it`, наружу
опубликован через Cloudflare Tunnel. Автодеплой — push в `main`
(`.github/workflows/deploy-prod.yml`), манифесты и подробности —
[`deploy/README.md`](deploy/README.md).

Ограничение: в проде **одна реплика** (комнаты, включая историю чата, живут
только в памяти процесса — см. «Приватность»), деплой = `Recreate`, а не
rolling update — на несколько секунд между остановкой старой версии и
готовностью новой сигналинг недоступен. Никакого volume/PVC в манифестах нет:
писать на диск приложению нечего.

### Живучесть звонка при деплое

Рестарт сервера (деплой новой версии, `Recreate`) НЕ рвёт сам звонок — рвётся
только WebSocket-сигналинг и теряется состояние комнаты в памяти процесса;
mesh (видео/аудио P2P, DataChannel-чат) физически не зависит от сигналинга и
продолжает работать напрямую между браузерами участников, пока сигналинг
недоступен:

- **Восстановление комнаты**: `PUT /api/rooms/{roomId}` — идемпотентный
  «upsert»: если комнаты нет — создаёт пустую с ЗАДАННЫМ id (`201`), если уже
  есть — просто подтверждает (`200`); кривой формат id — `400`. Комнаты
  эфемерны и не имеют отдельного контроля доступа (секрет — сам `roomId` в
  ссылке), поэтому восстановление по уже известному клиенту id ничего не
  расширяет по доступу (см. `src/main.rs::restore_room`).
- **Сохранение peerId**: `join-room` принимает опциональный `peerId` — если
  это валидный UUID и он ещё не занят в комнате, сервер использует его вместо
  генерации нового. При переподключении со СТАРЫМ peerId остальные участники
  узнают «вернувшегося» через штатный `peer-joined` и не пересоздают mesh —
  соединение к нему как было живым (сервер не участвовал), так и остаётся.
- **Авто-reconnect на фронте** (`static/room.js`): неожиданный обрыв
  сигналинга (не «Покинуть», не `room-not-found`/`room-full`) НЕ рушит
  интерфейс — тонкий баннер «Переподключение…» (не полноэкранный оверлей),
  попытки с бэкоффом 1с→2с→4с→8с (cap) в пределах ~2 минут суммарно.
  Последовательность одной попытки: открыть WS → `join-room` со своим
  прежним `peerId` → если `room-not-found` (сервер ничего не помнит после
  рестарта) → `PUT /api/rooms/{roomId}` → **новое** WS-соединение (сервер сам
  закрывает сокет сразу после отказа, см. `src/ws.rs`) → `join-room` снова.
  Успех — баннер убран, список участников сверен с `joined.peers`: те, кто
  ещё не успел переподключиться сам, получают грейс-период (~13с — остальные
  тоже переподключаются вразнобой) перед тем, как их тайл и mesh-соединение
  к ним реально закрываются; `peer-joined` для уже известного `peerId`
  идемпотентен (существующий mesh-пир не пересоздаётся). Если реконнект
  исчерпал бюджет — обычный терминальный оверлей «Соединение потеряно».
- **Шаринг экрана переживает деплой**: если участник шарил экран до обрыва
  — его локальный захват (`getDisplayMedia`) никуда не делся, после
  успешного reconnect он автоматически повторяет `share-start`; если кто-то
  успел перехватить экран, пока сервер восстанавливался — свой захват
  корректно останавливается (`share-rejected`). Если шарил кто-то другой —
  его сцена и так жива по mesh, `screenOwner` в свежем `joined` может быть
  `null`, пока владелец сам не переподключился — сцена не рушится
  немедленно, ей даётся тот же грейс-период.
- **Чат и его история** — целиком в клиентских буферах вкладок (сервер их и
  так никогда не хранил, см. «Приватность»), reconnect их не трогает вообще.
- **Version-skew баннер**: клиент запоминает версию (`/version.json`) при
  загрузке страницы и перечитывает её после каждого успешного reconnect;
  если она изменилась — ненавязчивый баннер «Вышла новая версия — обновите
  страницу» с кнопкой «Обновить» (без крестика). Протокол аддитивен, поэтому
  клиент со старым JS продолжает штатно работать и без перезагрузки.

## Протокол v4 (HTTP + WebSocket, JSON)

Симметричная комната: все участники равноправны в транспорте (mesh, каждый с каждым), но один из них — **лидер** с правом менять настройки комнаты и модерировать вход (см. «Права и лидер» выше); шаринг экрана — временное состояние комнаты (максимум один шарящий одновременно), комната живёт, пока в ней есть хоть один участник (плюс `EMPTY_ROOM_TTL_SECONDS` про запас для пустой). Начиная с v3 чат идёт напрямую между участниками по mesh RTCDataChannel (см. «Шина комнаты» выше) — WebSocket-протокол ниже несёт только сигналинг (offer/answer/ICE/stream-info), адресный fallback-релей чата и (с v4) управление правами/лобби. Протокол аддитивен — старый клиент, не знающий новых полей/типов, продолжает штатно работать (см. «Version-skew баннер»).

### HTTP

| метод + путь | тело запроса | ответ | назначение |
|---|---|---|---|
| `POST /api/rooms` | опционально `{"name": "..."}` (пока не используется, игнорируется) | `201 {"roomId": "<8 символов>", "leaderToken": "<uuid>"}` | создать новую ПУСТУЮ комнату; участники в неё ещё не входят — вход отдельным `join-room` по WebSocket; `leaderToken` — одноразовый, предъявляется создателем в своём `join-room`, чтобы стать лидером (см. «Права и лидер») |
| `PUT /api/rooms/{roomId}` | — | `201 {"roomId": ...}` (не было — создана пустая), `200 {"roomId": ...}` (уже была), `400` (кривой `roomId`) | идемпотентное восстановление комнаты после рестарта сервера (см. «Живучесть звонка при деплое»); токен лидера НЕ выдаёт — в восстановленной комнате лидером станет первый вошедший |
| `GET /r/{roomId}` | — | `200` HTML (`room.html`) | страница комнаты — короткая ссылка для участников |
| `GET /qr.svg?room={roomId}` | — | `200 image/svg+xml` (или `400`, если `room` не соответствует `^[a-z0-9]{8}$`) | QR-код, кодирующий `<proto>://<host>/r/{roomId}`; комната не проверяется на существование |

### WebSocket: клиент → сервер

Все сообщения — JSON с полем `type`. `offer`/`answer`/`ice-candidate`/`stream-info` сервер не разбирает по смыслу, только маршрутизирует от отправителя к `targetPeerId` (любому другому участнику той же комнаты). `chat` — тот же адресный релей: `envelope` для сервера опаковый JSON (не разбирается и не хранится), валидируется только размер (≤8КБ), rate-limit и право на чат (`guestChat`, см. «Права и лидер»); используется клиентом ТОЛЬКО как fallback, если DataChannel-шина до `targetPeerId` ещё не открыта — основной путь чата этот WebSocket вообще не трогает (см. «Шина комнаты» выше).

| type | поля | назначение |
|---|---|---|
| `join-room` | `roomId`, `name?` (имя участника), `peerId?` (свой ПРЕЖНИЙ peerId при переподключении, см. «Живучесть звонка при деплое»), `leaderToken?` (одноразовый токен из `POST /api/rooms` — совпал с хранимым, вошедший становится лидером) | вход в уже существующую комнату; если в комнате включено лобби (`lobbyEnabled`) и входящий не становится лидером — попадает в очередь ожидания вместо немедленного входа (см. «Права и лидер») |
| `offer` | `targetPeerId`, `sdp` | SDP-оффер любому другому участнику комнаты |
| `answer` | `targetPeerId`, `sdp` | SDP-ответ любому другому участнику комнаты |
| `ice-candidate` | `targetPeerId`, `candidate` | ICE-кандидат (trickle) любому пиру комнаты |
| `stream-info` | `targetPeerId`, `info` (опаковый JSON) | служебная информация между пирами, релеится как offer/answer/ICE |
| `chat` | `targetPeerId`, `envelope` (опаковый JSON, ≤8КБ) | адресный fallback-релей чата — только если DataChannel-шина до `targetPeerId` не открыта; гостю при `guestChat=false` — `error` вместо релея |
| `share-start` | — | заявка на шаринг экрана (удовлетворяется, только если экран сейчас свободен); гостю при `guestScreen=false` — `share-rejected {reason: "forbidden"}` независимо от того, свободен ли экран |
| `share-stop` | — | освобождение экрана (учитывается только от текущего владельца) |
| `update-settings` | `settings: {lobbyEnabled, guestChat, guestAudio, guestVideo, guestScreen}` | сменить настройки комнаты целиком — только лидер (иначе `error`) |
| `approve` | `peerId` | впустить ожидающего из лобби — только лидер |
| `reject` | `peerId` | отклонить ожидающего из лобби — только лидер |
| `leave` | — | явный выход (эквивалент закрытия сокета) |

### WebSocket: сервер → клиент

| type | поля | кому |
|---|---|---|
| `joined` | `peerId`, `peers: [{peerId, name}, ...]` (ДРУГИЕ участники, уже в комнате), `screenOwner` (`peerId` шарящего или `null`), `leaderId` (peerId текущего лидера), `settings` (текущие настройки комнаты), `pending: [{peerId, name}, ...]` (заявки лобби — заполнено ТОЛЬКО если вошедший сам лидер, иначе пустой массив) | новому (или одобренному лидером) участнику |
| `peer-joined` | `peerId`, `name` | остальным участникам комнаты |
| `peer-left` | `peerId` | остальным участникам комнаты |
| `offer` | `fromPeerId`, `sdp` | целевому участнику |
| `answer` | `fromPeerId`, `sdp` | целевому участнику |
| `ice-candidate` | `fromPeerId`, `candidate` | целевому участнику |
| `stream-info` | `fromPeerId`, `info` | целевому участнику |
| `share-started` | `peerId` | ВСЕМ участникам комнаты, включая инициатора (единый путь рендера) |
| `share-rejected` | `busyPeerId?` (кто занял экран — при конфликте занятости), `reason?` (`"forbidden"` — при отказе по правам, `guestScreen=false`; в этом случае `busyPeerId` отсутствует) | только инициатору `share-start` |
| `share-stopped` | `peerId` | всем участникам — по `share-stop` владельца, при его дисконнекте, либо когда лидер сам отобрал у него `guestScreen` во время шаринга |
| `chat` | `fromPeerId`, `envelope` | целевому участнику — fallback-релей, симметричный клиентскому `chat` выше |
| `waiting` | — | ожидающему в лобби сразу после `join-room`, вместо `joined` — до решения лидера |
| `join-request` | `peerId`, `name` | лидеру — новая заявка на вход (появилась либо при новом ожидающем, либо переслана заново при смене лидера) |
| `join-request-cancelled` | `peerId` | лидеру — ожидающий отвалился сам, не дождавшись решения |
| `join-rejected` | — | ожидающему — лидер отклонил заявку (или комната опустела целиком); сервер сам закрывает сокет сразу вслед |
| `settings-changed` | `settings` | всем участникам — лидер сменил настройки комнаты |
| `leader-changed` | `leaderId` | всем участникам — прежний лидер вышел, сервер назначил нового (самого раннего по времени входа) |
| `room-full` | — | участнику, если в комнате уже 6 участников |
| `room-not-found` | — | участнику: комната не создана / ещё не создана / удалена реапером |
| `error` | `message` | отправителю некорректного или запрещённого правами сообщения |
