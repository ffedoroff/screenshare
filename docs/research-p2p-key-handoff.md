# Исследование: передача секрета комнаты P2P вместо URL

> Статус: анализ, ничего не реализовано. 2026-07-16.
> Вопрос: можно ли убрать секрет из URL (оставить только короткий, но неподбираемый
> id комнаты), передавать ключ комнаты `k` от хоста участнику по P2P — только
> апрувнутым (лобби) или всем постучавшимся (без лобби) — **без единого компромисса**
> по сравнению с текущей моделью.

## 1. Что сегодня делает `#k` в URL — три роли одного секрета

Сегодняшний `k` (32 байта во фрагменте ссылки) выполняет одновременно три функции:

| Роль | Механизм |
|---|---|
| **Допуск** (admission) | Обладание ссылкой = право войти. Bearer-capability, никакой другой аутентификации нет — осознанно (security.md §9). |
| **Корень аутентификации против MITM** | SDP/ICE шифруются под K_sig=HKDF(k). Сервер-релей не может подменить DTLS-отпечатки: подделка не расшифруется (GCM-тег). Это работает **только потому, что общий секрет есть у сторон ДО первого сетевого обмена**. |
| **Бутстрап конфиденциальности** | K_meta (имена), корневой якорь всей E2E-модели. |

Ключевой факт для всего дальнейшего: **URL — это внеполосный канал** (хост передаёт
его гостю напрямую: мессенджером, голосом, QR), который сервер не контролирует.
Именно он делает MITM-защиту возможной.

## 2. Фундаментальное ограничение

Две стороны, не имеющие ни общего секрета, ни аутентичного открытого ключа друг
друга, **не могут** установить защищённый канал через посредника, контролирующего
весь их трафик (классика: DH без аутентификации ломается активным MITM). При входе
в комнату ВЕСЬ трафик гостя (WS-сигналинг, ICE, а значит и установление любого
«P2P»-канала) идёт через сервер.

Следствие: **что-то аутентифицирующее обязано приехать к гостю вне сервера — то
есть в ссылке**. Вопрос не «можно ли убрать всё из URL» (нельзя — это и был бы
компромисс), а «что минимально короткое и насколько несекретное URL может нести,
чтобы безопасность не просела».

Отсюда сразу два вердикта по идеям из постановки:

### 2.1. «В URL только server-visible id, сервер знает id→хост» — ОТКЛОНИТЬ

Если ссылка не содержит ничего, кроме id, который видит сервер (path/API), то:
- **Без лобби**: «отдавать k всем постучавшимся с валидным id» — сервер знает все
  id ⇒ сервер сам стучится и получает k. Сегодня сервер не может войти в комнату
  криптографически ни при каких условиях. Прямое ослабление.
- **С лобби**: апрув — человеческое решение по self-reported имени. Сервер стучится
  как «Вася с работы», хост апрувает. Сегодняшний допуск «обладание ссылкой»
  заменяется на «умение убедить хоста» — ослабление.
- MITM: серверу даже стучаться не нужно — он может встать в середину рукопожатия
  «гость↔хост», потому что гостю нечем проверить, что отвечает именно хост.

### 2.2. «IP-адрес хоста в id / пары id→IP на сервере» — ОТКЛОНИТЬ

- Технически мертво: браузер не умеет принимать входящие соединения (нет
  listening-сокетов), WebRTC требует обоюдного сигналинга через рандеву-сервер
  в любом случае, NAT/CGNAT/мобильные сети. «Достучаться по IP» в браузере некуда.
- Приватность хуже: сегодня IP участников видит только сервер на транспортном
  уровне (и не хранит — privacy.md §2). IP в ссылке/в выдаче по id раскрывает IP
  хоста всем обладателям ссылки и всем промежуточным логам. Регрессия.
- «Цифровая подпись секрета» в id: подпись не скрывает секрет и не заменяет его
  доставку; а вот **привязка открытого ключа хоста к ссылке** — рабочая идея,
  это вариант B ниже.

## 3. Жизнеспособные варианты

Общая схема у всех: URL = короткий роутинговый id (path, сервер видит) +
компактный аутентификатор во **фрагменте** (сервер не видит никогда). Гость по id
находит комнату через сервер, устанавливает с кем-то из участников аутентифицированное
эфемерное рукопожатие (ECDH поверх WS-релея и/или DataChannel), доказывает обладание
ссылкой, и участник отдаёт ему `k` внутри этого канала (сразу — без лобби; после
approve — с лобби). Сервер по-прежнему не хранит и не видит ни `k`, ни аутентификатор.

Различаются варианты тем, **что лежит во фрагменте**:

### Вариант B — публичный верификатор ключа хоста (рекомендуемый)

Фрагмент: `#a=<hash(pubkey_комнаты)>`, 96–128 бит (16–22 символа base64url).

- При создании комнаты клиент хоста генерирует эфемерную пару (ECDSA P-256 /
  Ed25519 — есть в WebCrypto). Ссылка несёт хэш открытого ключа.
- Гость проверяет предъявленный при рукопожатии pubkey против хэша из ссылки ⇒
  MITM-сервер должен предъявить ключ с тем же хэшем ⇒ offline-перебор ≥2^96.
- Гость доказывает обладание ссылкой, привязав знание `a` к транскрипту
  (HMAC/HKDF от `a`) ⇒ сервер, не видевший фрагмент, постучаться не может ⇒
  допуск остаётся «по обладанию ссылкой», как сегодня. Лобби — опциональный
  человеческий слой сверху, ровно как сейчас.
- **Философски чисто: во фрагменте больше нет секрета вообще** — только публичный
  верификатор. Утечка URL в логи/скриншоты после встречи не даёт ничего
  (см. §5 про forward secrecy).
- Чтобы «раздавать» мог не только создатель: вместе с `k` каждому принятому
  участнику передаётся и приватный ключ комнаты — тогда постучавшегося обслуживает
  любой, кто онлайн (см. §6 про доступность).

### Вариант D — симметричный бутстрап-токен (инженерно проще)

Фрагмент: `#t=<токен 96–128 бит>`. Рукопожатие: эфемерный ECDH, транскрипт
подписан HMAC(HKDF(t)) с обеих сторон — токен играет ту же роль, что сегодня `k`,
но **только в момент рукопожатия**; сам ключ комнаты доставляется внутри.

- Реализуется целиком на WebCrypto (ECDH + HKDF + HMAC), минимум нового кода.
- Минус: в URL формально остаётся секрет (короче и одноразовее по смыслу, но
  секрет). Пассивный наблюдатель рукопожатия может проверять кандидатов токена
  offline по HMAC-тегам ⇒ ниже ~96 бит укорачивать нельзя.
- Это наименьшее отклонение от буквы задачи («секрет не через URL» — не выполнено,
  выполнено «ключ шифрования не через URL»).

### Вариант C — PAKE (самая короткая ссылка, самая дорогая реализация)

Фрагмент: короткий код (можно 6–10 символов, даже ~40 бит). Гость и хост гоняют
PAKE (CPace/SPAKE2) через релей: offline-атака на короткий код невозможна по
построению, активный MITM получает ровно одну online-попытку угадать код на
рукопожатие, и каждая неудача видна хосту (можно жёстко лимитировать).

- Единственный способ получить ссылку заметно короче 16+ символов аутентификатора
  **без** снижения стойкости.
- Минусы: в WebCrypto нет PAKE и нет hash-to-curve; понадобится либо аккуратная
  собственная реализация поверх X25519/P-256 (криптографический риск, противоречит
  принципу проекта «только WebCrypto, никаких библиотек»), либо внешняя
  аудированная библиотека (противоречит «no build, no deps»). Для проекта, чья
  главная фича — проверяемая простота криптослоя, это серьёзный довод против.

### Сравнение

| | Сегодня (`#k`) | B (верификатор) | D (токен) | C (PAKE) |
|---|---|---|---|---|
| Секрет шифрования в URL | **да, навсегда** | нет | нет | нет |
| Какой-либо секрет в URL | да | **нет (публичный хэш)** | да (бутстрап) | да (короткий код) |
| Длина фрагмента | 43 симв. | 16–22 | 16–22 | 6–10 |
| Пассивный сервер | ✔ | ✔ | ✔ | ✔ |
| Активный сервер-релей (подмена SDP) | ✔ | ✔ | ✔ | ✔ |
| Сервер стучится и получает k | невозможно | невозможно | невозможно | невозможно |
| Retro-расшифровка записанного трафика при поздней утечке ссылки | **возможна** | нет (PFS) | нет (PFS) | нет (PFS) |
| Атака на канал доставки ссылки | SAS | SAS | SAS | SAS |
| Новая криптография | — | ECDSA/ECDH (WebCrypto) | ECDH+HMAC (WebCrypto) | PAKE (нет в WebCrypto) |
| Новый код/протокол | — | средне | мало | много |

Во всех трёх вариантах SAS остаётся и нужен ровно для того же, что сегодня:
атакующий, контролирующий сам канал доставки ссылки, по-прежнему вне модели `k`
(и вне модели `a`/`t`) — это не регрессия, это тот же известный пробел
(sas-verification.md §8). В варианте B SAS можно в будущем дополнительно привязать
к ключу комнаты (мелкое усиление, не обязательное).

## 4. Требования к энтропии («короткий, но неподбираемый»)

Две разные величины, которые нельзя путать:

1. **Роутинговый id** (path, сервер видит): защищает только от online-перебора
   посторонними. Сегодня 8 символов ≈ 39.6 бит + rate-limit'ы — этого достаточно
   и в новой схеме (неудачные «стуки» дополнительно видны участникам). Можно
   оставить как есть.
2. **Аутентификатор во фрагменте**: против него возможна **offline**-атака
   (перебор ключевых пар под хэш в B; перебор токена по перехваченным HMAC в D) ⇒
   минимум ~96 бит, комфортно 128. Урезать ниже — уже компромисс, кроме варианта C,
   где PAKE снимает offline-класс атак целиком.

Красивый трюк для «в URL только id»: **id = усечённый хэш аутентификатора**
(`roomId = H(a)[..8]`), ссылка вида `/j#<один токен 22 символа>` — страница сама
вычисляет роутинговый id и шлёт серверу только его. В URL ровно один короткий
компонент, сервер видит производную, фрагмент не видит никогда.

## 5. Что новая схема даёт СВЕРХ сегодняшней

- **Forward secrecy**: сегодня `k` статичен и лежит в ссылке вечно — кто записал
  зашифрованный релей-трафик и потом добыл ссылку (история мессенджера, скриншот),
  расшифрует задним числом. В B/D/C ключ доставляется через эфемерный ECDH:
  утечка ссылки после встречи не даёт ничего.
- В B из URL исчезает секрет как класс: ссылку можно светить в логах/адресной
  строке без последствий для конфиденциальности (допуск в живую комнату — отдельно,
  через лобби).
- Криптографическая привязка допуска: сегодня злонамеренный сервер может «впустить»
  кого угодно в комнату на уровне membership (расшифровать тот всё равно ничего
  не сможет); в новой схеме это так же бессмысленно — k не выдаётся без
  доказательства обладания ссылкой.

## 6. Цена: доступность и UX (честный список)

Это не компромиссы по криптостойкости, но реальные изменения поведения:

1. **Ключ выдаёт живой участник.** Вход в пустую (но ещё живую по TTL) комнату
   невозможен: постучаться можно, получить k не у кого — жди участника. Сегодня
   гость со ссылкой входит в пустую комнату свободно.
2. **F5 последнего участника = смерть комнаты.** Сегодня `#k` в адресной строке
   переживает перезагрузку; в новой схеме k живёт только в памяти вкладки, и если
   перезагрузился последний держатель ключа — включая самого хоста — раздать k
   больше некому. Комнату придётся пересоздавать. Смягчения без нарушения принципа
   «никакого storage» нет (sessionStorage нарушил бы задокументированные обещания
   privacy.md). Частично лечится тем, что ключи раздают ВСЕ участники (не только
   создатель), — умирает комната только при одновременном уходе всех.
3. **+1–2 RTT и зависимость от онлайна раздающего** при каждом входе (включая
   реконнект с новым peerId после F5 гостя).
4. **Больше протокола = больше поверхности**: стук, выдача, делегация ключей новым
   участникам, анти-DoS на стуки (готовый образец — лобби с его MAX_PENDING=10 и
   per-IP лимитами). Каждая строчка нового криптокода — против главного актива
   проекта (маленький проверяемый криптослой).
5. **Семантика ссылки меняется** и это надо честно переписать в privacy.md/README:
   «ссылка = ключ» превращается в «ссылка = право постучаться; ключи выдают живые
   участники». С лобби это строго лучше при утечке ссылки; без лобби — эквивалент
   сегодняшнего.

## 6.5. Вариант E — PFS **и** переживание F5 одновременно (дополнение 2026-07-16)

**Реализовано 2026-07-16** — см. [`e2e-encryption.md`](e2e-encryption.md).

Требование пары «forward secrecy + F5 переживается» вскрывает, что конфликт в §6
был не между PFS и перезагрузкой, а между PFS и **отсутствием секрета в URL**.
Если ослабить только второе — оставить в URL статический секрет, но запретить ему
шифровать трафик — оба свойства достижимы одновременно.

### 6.5.1. Уточнение: что именно сегодня расшифровывается задним числом

Медиа и чат уже обладают PFS: они идут P2P поверх DTLS/DTLS-SRTP, ключи которых
выводятся из эфемерного ECDHE самого DTLS-рукопожатия — записанный P2P-трафик
поздней утечкой ссылки **не** вскрывается уже сейчас. Ретро-уязвим только
релей-слой под статическими K_sig/K_meta: **SDP (включая DTLS-отпечатки),
ICE-кандидаты (то есть IP-адреса участников), stream-info, display-имена**.
Это метаданные, но чувствительные (IP!). Именно их и нужно перевести на PFS.

### 6.5.2. Схема

Во фрагменте остаётся статический токен `t` (как сегодняшний `k`, можно 128 бит
/ 22 символа), но он становится **чисто аутентификационным**: сам по себе он
больше ничего не расшифровывает.

- При каждом входе вкладка генерирует эфемерную ECDH-пару. Эфемерный публичный
  ключ — несекретный, его можно возить прямо в `join-room` / `joined` /
  `peer-joined` (сервер видит — не страшно).
- Для каждой пары участников (A,B) сессионные ключи сигналинга выводятся из
  эфемерного ECDH(A,B), а транскрипт (roomId, peerId'ы, оба эфемерных ключа)
  подтверждается HMAC под K_auth = HKDF(t, "auth-v1"). Это классический паттерн
  Noise-с-PSK / SIGMA: PSK даёт взаимную аутентификацию (сервер без `t` не может
  ни вклиниться, ни постучаться), ECDHE даёт PFS. Реализуется целиком на
  WebCrypto (ECDH P-256/X25519 + HKDF + HMAC), без новых примитивов.
- SDP/ICE/stream-info шифруются попарными сессионными ключами вместо общего
  K_sig. Релей и так попарный (offer от A к B) — групповой ключ не нужен.
- Имя участника: вместо room-wide K_meta — шифровать на «анонсированный»
  эфемерный ключ адресата (лидеру в лобби ключ доставляется в `waiting`/`join-request`
  обвязке; обычным пирам — в `peer-joined`). Гранулярность PFS для имён — время
  жизни вкладки адресата; этого достаточно.
- По завершении вкладки эфемерные ключи умирают → записанный релей-трафик не
  вскрывается даже при полной утечке `t`.

### 6.5.3. Свойства

| | Сегодня (`#k`) | E (`#t` + эфемерные сессии) |
|---|---|---|
| F5 / пустая комната / поздний вход / «живой держатель» | ✔ | ✔ идентично сегодняшнему |
| Пассивный сервер / активный relay-MITM | ✔ | ✔ (PSK-аутентификация) |
| Сервер стучится / входит | невозможно | невозможно (`t` не видит) |
| Ретро-расшифровка записанного релея при поздней утечке ссылки | IP, SDP, имена | **ничего (PFS)** |
| Утечка ссылки во время жизни комнаты | полный доступ | полный доступ (эквивалентно, осознанно) |
| Медиа/чат ретро | уже PFS (DTLS) | уже PFS (DTLS) |
| Секрет в URL | да, расшифровывающий | да, но **только аутентифицирующий** |
| Длина фрагмента | 43 симв. | 22 симв. |
| Доп. RTT при входе | — | ~0 (эфемерные ключи ездят в существующих join-сообщениях) |
| SAS | нужен для атаки на канал доставки ссылки | без изменений |

Вариант E — строгое Парето-улучшение текущей модели: ни одно свойство не
ухудшается, ретро-приватность релея (IP/SDP/имена) появляется, ссылка укорачивается
вдвое, UX не меняется вообще. Цена — протокольная работа: попарные сессии вместо
одного room-wide ключа (обвязка рукопожатия в join-флоу, замена K_sig/K_meta,
миграция форматов, транскрипт против replay/cross-room — всё по учебнику Noise-psk).

Вариант B из §3 при этом не отменяется: это ортогональная следующая ступень
(«в URL вообще нет секрета»), которую можно когда-нибудь предложить как опцию
для комнат, где приемлема цена «живого держателя» (§6). Но требованиям «PFS + F5»
отвечает именно E.

## 6.6. Время жизни внутри токена (дополнение)

**Реализовано 2026-07-16** — см. [`e2e-encryption.md` §2.2](e2e-encryption.md#22-expiry-e--a-cryptographic-boundary-not-a-runtime-check).

Вопрос: даёт ли что-то встраивание срока действия в токен/секрет («после 3 часов
с этим токеном войти нельзя»)?

Ключевое: срок действия — **политика, а не криптография**. Время нельзя обеспечить
криптографически без доверенной стороны: проверять его будет чей-то код по чьим-то
часам. Отсюда три следствия:

1. **Против ретро-расшифровки — бесполезно.** Записанный шифртекст не спрашивает,
   «действителен» ли ещё токен: если ключ выводим из токена (сегодняшний `k`),
   поздняя утечка вскрывает запись независимо от любых меток времени. Ретро-приватность
   даёт только эфемерный DH (вариант E), не expiry.
2. **Против позднего входа — избыточно.** Сервер уже жёстко убивает комнату через
   3 часа (MAX_ROOM_LIFETIME) и пустую — через 120 секунд; мёртвый roomId не
   маршрутизируется, ссылка и так бесполезна. Expiry в токене дублирует это.
3. **Единственный реальный выигрыш — E2E-бэкстоп против самого сервера.** Сегодня
   лимит жизни комнаты держится только на честности сервера: злонамеренный/сломанный
   сервер может держать комнату живой бесконечно, растягивая окно входа по утёкшей
   ссылке. Если срок зашит в токен и его проверяют **клиенты** (в варианте E —
   бесплатно: включить expiry в HKDF-info, `K_auth = HKDF(t, "auth-v1" ‖ expiry)`;
   отдельная подпись не нужна — сторона с иным expiry просто не сойдётся по ключу,
   «отрезать» метку нельзя), то честные участники откажут в рукопожатии после
   срока, что бы ни думал сервер. Это соответствует философии проекта «не доверяем
   серверу», но защищает узкий сценарий: утечка ссылки + сервер, злонамеренно
   продлевающий комнату + внутри всё ещё есть честные участники.

Издержки: рассинхрон часов клиентов (ложные отказы), чуть длиннее URL (метка
должна ехать во фрагменте), и риск ложного чувства защищённости («ссылка протухла —
можно не волноваться об утечке» — неверно для ретро-расшифровки, см. п.1).

Вердикт: как самостоятельная мера — бесполезная добавка (дублирует серверный
лимит, ничего не даёт криптографически). Как копеечное усиление внутри варианта E
(expiry в HKDF-info) — осмысленный E2E-бэкстоп против сервера-нарушителя; брать
стоит только в этой форме. Отдельно заиграет, если когда-нибудь появятся
персистентные/повторяющиеся комнаты — там короткоживущие инвайт-токены,
отделённые от секрета комнаты, станут полноценным механизмом.

## 7. Рекомендация

0. Если требование — «forward secrecy + перезагрузка страницы переживается»
   (уточнение заказчика от 2026-07-16): **вариант E (§6.5)** — единственный,
   дающий оба свойства сразу, и при этом Парето-улучшение текущей модели без
   изменений UX. Остальные пункты ниже — для исходной постановки «секрета в URL
   нет вообще».
1. Если цель — «ключ шифрования никогда не в URL, безопасность не ниже, ссылка
   заметно короче»: **вариант B** (публичный верификатор во фрагменте, ключи
   раздают все участники, лобби — опция сверху). Это единственный вариант, где
   URL перестаёт содержать секреты вообще, и он даёт бонусом forward secrecy.
   Ссылка: `https://…/j#Ab3xK9…22симв` (≈ вдвое короче сегодняшней).
2. Если цель — минимальный дифф и PFS, а буква «без секрета в URL» не принципиальна:
   **вариант D** (той же длины ссылка, сильно проще протокол).
3. **Вариант C (PAKE)** держать как дальний прицел «ссылка из ~8 символов» — он
   криптографически честен, но требует PAKE-примитива, которого нет в WebCrypto;
   для этого проекта цена в сложности/доверии к реализации сейчас перевешивает.
4. Идеи «id→IP хоста» и «голый server-visible id» — отклонить (см. §2.1–2.2):
   первая инфраструктурно невозможна в браузере и ухудшает приватность, вторая
   строго слабее текущей модели в обоих режимах (с лобби и без).

Главный трейд-офф решения в целом — §6.1–6.2: комната начинает требовать живого
держателя ключа. Если это неприемлемо для сценариев «скинул ссылку, люди
подтягиваются когда смогут», текущая модель `#k` остаётся оптимальной, а выигрыши
B сводятся к «короче ссылка + PFS» против «комната умирает вместе с последней
вкладкой».
