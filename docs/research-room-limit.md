## 1. Зачем это может быть нужно

Три заявленных сценария — и честная сверка каждого с тем, что лобби
(`lobbyEnabled`, см. [`permissions-and-leader.md` §6](permissions-and-leader.md#6-the-waiting-room-lobby))
уже даёт сегодня:

| Сценарий | Ценность лимита | Дублирует ли лобби? |
|---|---|---|
| **1-на-1 звонок, куда нельзя вломиться третьему даже со ссылкой** | Средняя-высокая. Лобби решает ту же задачу, но требует, чтобы лидер **был у экрана и лично отклонил** каждого третьего — если он отвернулся (взял кофе, ушёл в другое окно) в момент, когда кто-то стучится по слитой/угаданной ссылке, лобби не спасает автоматически: заявка просто висит, пока лидер её не увидит, и пока он молчит, третий участник — не в комнате, но и не отклонён, состояние подвешено. Лимит `maxParticipants=2` закрывает дверь автоматически и сразу, без участия человека. | Нет, не дублирует — разное время реакции: лобби = решение по каждому случаю **в моменте**, лимит = правило **навсегда, без надзора**. |
| **«Вебинар на троих»** | Низкая-средняя. Это частный случай сценария 1-на-1, только порог не 2, а N. Ценность та же логика: комфортно "закрыть дверь" на конкретном числе без необходимости отклонять каждого лично. | Нет — то же рассуждение, что выше, просто другое N. |
| **Экономия трафика мобильных участников** (лидер знает состав аудитории заранее) | Низкая. Проблема реальная (mesh — исходящий трафик каждого клиента растёт как *n*-1, см. `src/state.rs` комментарий у `DEFAULT_MAX_PARTICIPANTS`), но лимит участников решает её очень грубо — либо пускаем N-го, либо нет, без разбора, кто у него канал слабый. Лидер и так не может заранее знать, кто зайдёт с мобильного, а кто с десктопа: лимит применяется к **порядку захода**, а не к качеству сети конкретного человека. | Не конкурирует с лобби вообще — другая ось (трафик, не допуск). |
| **Вежливое «комната заполнена» вместо неожиданных гостей** | Средняя, чисто UX. Сегодня «неожиданный гость» либо получает `room-full` (если уже упёрлись в серверный потолок — событие редкое при дефолте 6), либо просто входит (если лобби выключено) — везде, кроме серверного потолка, «неожиданности» и так не бывает **при выключенном лобби**, потому что вообще никто не проверяется. Лимит превращает «войти может кто угодно» в «войти может кто угодно, пока не занято N слотов» — управляемая версия того же самого без ручного контроля. | Нет — при выключенном лобби это ЕДИНСТВЕННЫЙ механизм контроля численности вообще, кроме серверного потолка. |

**Итог по ценности**: лимит не дублирует лобби — они решают разные грани одной
проблемы («кто может войти» vs «сколько всего может быть»), и разница
принципиальна: **лобби требует живого решения лидера по каждой заявке, лимит
работает без надзора**. Самый сильный сценарий — 1-на-1 звонок с
`lobbyEnabled=false` (обычно так и хотят: не хочется одобрять единственного
собеседника вручную) и потолком именно 2 — то есть **лимит нужнее всего именно
там, где лобби включать не хотят**. Экономия трафика — самая слабая мотивация
из четырёх, ей стоит уделить минимум веса в приоритизации.

## 2. Дизайн

### 2.1 Поле в `RoomSettings`

```rust
// src/protocol.rs
#[serde(rename_all = "camelCase")]
pub struct RoomSettings {
    #[serde(default)]
    pub lobby_enabled: bool,
    #[serde(default)]
    pub max_participants: Option<usize>,   // None = «серверный потолок» (крутится вместе с ним)
    // ...guest_* как раньше
}
```

`Option<usize>` с `None` по умолчанию, а не «зафиксированное число при
создании комнаты» — сознательно: `MAX_PARTICIPANTS` читается из env один раз
на процесс (`LazyLock`, `src/main.rs`), но если сервер перезапустят с другим
значением env, а комната переживёт рестарт через `PUT /api/rooms/{id}`
(`restore_room`, `src/main.rs:449-466`), она и так получает
`RoomSettings::default()` заново (см. [§4](#4-взаимодействие-с-фичами) про
рестарт) — `None` корректно «следует» за новым потолком автоматически, а
зашитое число было бы тихо неверным (и невалидным, если новый потолок ниже
старого зашитого числа).

Валидация — только в `handle_update_settings` (`src/ws.rs:574-614`), при
обработке `update-settings`: если `settings.max_participants` есть и **не**
`2..=*crate::MAX_PARTICIPANTS` — отказ (`error`, настройки не применяются),
без частичного применения остальных полей (сохраняем текущую механику «целиком
или ничего» — `settings` уже применяется атомарно одним `room.settings =
settings.clone()`). Нижняя граница 2, а не 1: комната с лимитом 1 не имеет
смысла (лидер сам не сможет никого впустить, включая себя — он уже занимает
единственный слот) — 1 просто отклоняем как невалидный ввод, не как
специальный кейс «соло-комната».

### 2.2 Что делать, если текущих участников уже больше нового лимита

**Не выгонять** — согласен с интуицией задачи. Обоснование: у сервера и так нет
эффективного «мягкого» способа выгнать одного конкретного участника (нет
`kick`/`ban` в протоколе вовсе — это отдельная нереализованная фича), а
насильственный дроп чьего-то WebRTC-соединения без предупреждения — гораздо
худший UX, чем «лимит теперь чисто блокирует будущих новеньких». Практическое
следствие: `room.settings.max_participants` при проверке в `join-room` и
`approve` сравнивается **не** с `room.participants.len() >=
*crate::MAX_PARTICIPANTS` (как сейчас, `src/ws.rs:390` и `:638`), а с эффективным
лимитом:

```rust
fn effective_max_participants(&self) -> usize {
    self.settings.max_participants.unwrap_or(*crate::MAX_PARTICIPANTS)
}
```

Если `participants.len() > effective_max_participants()` (лидер снизил лимит
ниже текущей занятости) — это просто означает, что **все** дальнейшие
`join-room`/`approve` от кого угодно (включая уже одобренных из лобби) получат
`room-full`, пока состав не поредеет сам естественным образом (кто-то вышел).
Никакого специального состояния "over capacity" не заводим — сравнение `>=` уже
корректно обрабатывает и `==`, и `>` без дополнительного кода.

### 2.3 UI

По образцу переключателей прав гостей в панели настроек лидера
(`static/room.html:290-360`, `static/room.js` — `wireSettingToggle`,
`static/room.js:2368-2372`, вызываемый для каждого `<input type="checkbox">` в
`syncSettingsPanelInputs`, `static/room.js:1589-1596`): аналогичная функция
`wireSettingSelect`, но на `<select id="setting-max-participants">`, а не на
чекбоксе. Опции — от 2 до текущего `maxParticipants` (серверный потолок,
клиент его уже знает из `joined.maxParticipants`, `static/room.js:329`), верхний
пункт помечен как «No limit (server max: N)» и на wire кодируется как
`null`/отсутствие поля, а не число N — важно: если сервер потом перезапустят с
другим потолком, ранее выставленное клиентом число N осталось бы неверно
зафиксированным, а `null`/`None` продолжает означать «без своего лимита» и
корректно подхватывает новый потолок (см. [§2.1](#21-поле-в-roomsettings)).

Обязательный, отдельный от чекбоксов момент: `settings-changed`
(`static/room.js:3178-3183`) сегодня обновляет только `roomSettings`, но
переменная `maxParticipants` (`static/room.js:329`, читаемая счётчиком
участников `static/room.js:1249` и текстом `room-full`-оверлея
`static/room.js:3223`) — **отдельная** top-level переменная, никак не связанная
с `roomSettings`. Без явного изменения в обработчике `settings-changed`
(добавить `maxParticipants = settings.maxParticipants ?? SERVER_MAX;
updateParticipantCount();`) счётчик и текст «Room is full» в реальном времени
**не обновятся** при смене лимита лидером во время звонка — это не «мелочь»,
а отдельная, легко забываемая точка правки.

### 2.4 Что с `pending` в лобби при снижении лимита

Ничего специального делать не нужно — заявки в лобби **уже сегодня** не
проверяются против `MAX_PARTICIPANTS` в момент постановки в очередь (`src/ws.rs`,
ветка `lobby_enabled` в `JoinRoom`, строки 334-388) — только против отдельного
`MAX_PENDING` (10, щедрый и независимый лимит очереди ожидания). Проверка
против потолка участников происходит только в момент `approve`
(`src/ws.rs:621-646`) — если к этому моменту место кончилось (в том числе
потому что лидер СНИЗИЛ лимит, пока заявка висела), `approve` уже сегодня
отвечает и ожидающему (`RoomFull`), и лидеру (`error: room is full, cannot
approve`) без падения инварианта. Единственное изменение — этот код должен
сравнивать с `effective_max_participants()`, а не с константой напрямую (см.
[§2.2](#22-что-делать-если-текущих-участников-уже-больше-нового-лимита)); заявки
сами по себе никак не «протухают» и не отклоняются автоматически при смене
лимита — лидер как и раньше решает по каждой руками, просто теперь `approve`
части из них будет отказывать.

Все изменения аддитивны (новое `Option`-поле с `#[serde(default)]`, старые

т.е. ведут себя ровно как сегодня):

| `src/protocol.rs` | Поле `max_participants: Option<usize>` в `RoomSettings` | 0.5ч |

| `docs/permissions-and-leader.md`, `docs/signaling-protocol.md` | Документирование нового поля и правила «блокирует новых, не выгоняет старых» | 1ч |

формы `RoomSettings` где-либо на диске не существует).

## 3. Безопасность/приватность

- **Server-side truth, как и membership** (`permissions-and-leader.md` §1): да,
  и это не новый компромисс. Сервер уже сегодня — единственный источник истины
  и для `room-full` относительно серверного потолка, и для того, кто лидер, кто
  участник, кто в лобби. Лимит лидера просто добавляет ещё одно число, которое
  сервер применяет ровно тем же кодовым путём (`join-room`/`approve`), что уже
  применяет `crate::MAX_PARTICIPANTS`. Если считать, что «сервер может
  игнорировать лимит лидера» — компромисс, то тем же рассуждением сервер «может
  игнорировать» вообще любую свою собственную проверку (в т.ч. сегодняшний
  `room-full`) — это тавтология про доверенный сервер, а не новая уязвимость:
  self-hosting-модель проекта (см. `docs/self-hosting.md`) и так предполагает,
  что оператору сервера **доверяют по определению** (он видит SDP/ICE до
  шифрования на уровне транспорта TLS и т.п.). Никакого дополнительного
  доверия здесь не требуется сверх того, что участники уже оказывают сегодня.
- **E2E-модель не затрагивается**: подтверждено по коду — `RoomSettings`
  целиком идёт как открытый JSON и сегодня (`guestChat`/`guestAudio`/... в
  `settings-changed`/`joined` — нигде не шифруются, в отличие от `name`, которое
  с Ш1/E2E v2 шифруется отдельным `name-announce`, см. `src/protocol.rs`
  комментарий модуля и `docs/e2e-encryption.md`). Число участников — не секрет
  и сегодня (`Joined::max_participants` уже отдаётся в открытом виде,
  `src/protocol.rs:178-185`); добавление ещё одного открытого числа рядом ничего
  не меняет в модели угроз шифрования.
- **DoS-угол — здесь есть реальный, не вполне очевидный эффект, и он не в пользу
  фичи**: лимит **усугубляет**, а не облегчает атаку «злоумышленник со ссылкой
  занимает слоты до честных гостей». При серверном потолке 6 нужно 6
  паразитных соединений, чтобы забить комнату для всех; при лидерском лимите 2
  (флагманский сценарий §1 — «1-на-1, куда нельзя вломиться») достаточно **одного**
  паразитного соединения, чтобы забить комнату для второго легитимного участника
  — то есть чем меньше настроенный лимит, тем **дешевле** атака отказа в
  обслуживании тем, кто знает (или подобрал/увидел через плечо) ссылку. Лобби
  (`lobbyEnabled`) — уже сегодня единственный реальный ответ на этот вектор
  (он не даёт занять слот без решения лидера вообще, независимо от числа
  слотов), лимит его никак не усиливает и не заменяет. Практический вывод для
  UI/документации: **если лидер ставит маленький `maxParticipants` ради
  приватности «1-на-1», ему стоит явно посоветовать заодно включить лобби** —
  иначе маленький лимит без лобби делает комнату *более* уязвимой к захвату
  единственного слота, чем комната без лимита вовсе (у которой просто больше
  «запасных» слотов). Это стоит явно проговорить в UI (тултип/подсказка рядом
  с селектом) и в `docs/security.md` (раздел H2/M3), а не только в этом файле.

## 4. Взаимодействие с фичами

- **Смена лидера**: лимит — часть `Room::settings`, не завязан на
  `Room::leader_id` никак — переживает смену лидера автоматически, без единой
  строчки специального кода (`cleanup_peer`, `src/ws.rs:930-1017`, не трогает
  `room.settings` вовсе).
- **Реконнекты — единственный по-настоящему тонкий момент, и именно он бьёт по
  флагманскому сценарию 1-на-1.** Клиентский `peer_id` при `join-room`
  принимается повторно только если он **ещё не занят** ни в `participants`, ни в
  `pending` этой комнаты (`src/ws.rs:308-315`, комментарий явно это
  документирует). Обрыв WS-сигналинга детектируется сервером не мгновенно —
  хартбит `PING_INTERVAL=20с` + `MAX_MISSED_PONGS=2` (`src/ws.rs:98-102`) даёт
  окно до ~40-60 секунд, в течение которого «зависшая» старая запись
  участника **всё ещё занимает слот** в `room.participants`, хотя сокет уже мёртв.
  Фронтовый авто-reconnect (`static/room.js`, `RECONNECT_BACKOFF_MS`) пытается
  переподключиться уже через 1-8 секунд — то есть **быстрее**, чем сервер
  успевает выкинуть зависшую старую запись. Сегодня, при дефолте 6 участников,
  это почти никогда не проявляется (лишний «зомби»-слот на фоне 5 свободных не
  страшен). Но именно во флагманском сценарии **1-на-1 с `maxParticipants=2`**
  это становится реальной проблемой: если участник A на секунду теряет
  сигналинг (не медиа — mesh переживает обрыв сигналинга, см.
  `docs/self-hosting.md`, «Surviving a Restart/Redeploy») и клиент пытается
  реконнектнуться, а его старая запись ещё не вычищена реапером/хартбитом —
  комната формально уже «полна» (зомби-A + живой B = 2/2), и новый `join-room`
  от A получит **`room-full`** — то есть от собственного одного и того же
  человека. Реконнект в этом же коде уже пытается передать прежний `peer_id`
  именно для таких случаев (комментарий `src/ws.rs:308-315`), но проверка
  занятости слота всё равно основана на количестве *записей*, а не на
  количестве уникальных людей — с маленьким лимитом это расхождение становится
  заметным на практике. **Рекомендация**: если фича будет реализована,
  отдельно протестировать реконнект именно в комнате с `maxParticipants=2` и,
  возможно, либо (а) документировать это как известное ограничение, либо (б)
  рассмотреть более агрессивный хартбит для маленьких комнат, либо (в) особый
  путь реконнекта, который сначала явно завершает старую запись при совпадении
  `peer_id, room_id` до момента истечения хартбита — это нетривиальная правка
  с последствиями для конкурентности (два сокета временно претендуют на один
  `peer_id`) и в объём оценки §2.5 **не включена** — если решите делать лимит,
  закладывайте на это отдельное расследование.
- **Waiting room / `MAX_PENDING`**: полностью независимые лимиты уже сегодня
  (см. [§2.4](#24-что-с-pending-в-лобби-при-снижении-лимита)) — `MAX_PENDING=10`
  ограничивает саму очередь ожидания, никак не завязан на
  `maxParticipants`/`MAX_PARTICIPANTS`. Никаких изменений в этот механизм не
  требуется, только сравнение при `approve` должно использовать эффективный
  лимит комнаты, а не константу.
- **Восстановление комнаты после рестарта сервера (`PUT /api/rooms/{id}`)**:
  проверено — `restore_room` (`src/main.rs:425-475`) при отсутствующей
  записи создаёт `Room` с `settings: RoomSettings::default()`
  (`src/main.rs:459`) — **это уже сегодня истинно для ВСЕХ полей `RoomSettings`,
  не только для будущего `max_participants`**: `lobbyEnabled`, `guestChat` и
  прочие настройки, выставленные лидером до рестарта, **не переживают
  рестарт вовсе** — восстановленная комната всегда стартует с чистого дефолта,
  независимо от того, что было настроено раньше. Это не новая проблема,
  вносимая лимитом, а уже существующее, документированное поведение (in-memory
  state, `docs/self-hosting.md` §7.1) — `max_participants` просто наследует его
  на равных с остальными полями, никакого дополнительного кода на этот случай
  не требуется, но стоит явно упомянуть в документации рядом с описанием поля,
  чтобы не создавалось ложного ожидания «лимит переживёт рестарт, как и всё
  остальное в этом проекте не переживает».
- **`maxParticipants` в UI счётчика**: сегодня `Joined::max_participants`
  (`src/protocol.rs:178-185`) уже задуман как «покажи `N / <это значение>»,
  не захардкоженную `/6`» — естественное расширение: то же поле начинает
  нести не серверный потолок, а *эффективный* лимит комнаты (который до этой
  фичи всегда совпадал с серверным потолком) — переименования/добавления
  нового поля на wire не требуется, только смена того, что сервер туда
  подставляет (`admit_participant`, `src/ws.rs:542-551`, заменить
  `*crate::MAX_PARTICIPANTS` на `room.effective_max_participants()`). Требуется
  только не забыть держать в синхроне с `settings-changed` (см.
  [§2.3](#23-ui)) — иначе счётчик у уже подключённых участников не обновится
  при смене лимита посреди звонка.

## 5. Вердикт

> Реализовано 2026-07-16 (минимально жизнеспособный вариант из этого раздела:
> серверная часть + `<select>` в панели настроек лидера).

**Делать стоит, но не в первую очередь.** Ценность реальна и не дублирует
лобби — комбинация «маленький лимит + без лобби» закрывает конкретный, часто
запрашиваемый у видеозвонков кейс («звонок только для двоих, без ручного
одобрения»), которого сегодня в принципе нет способа выразить, кроме как
попросить незваного гостя выйти голосом после того, как он уже вошёл. Но:

- Реализация **дешёвая** (7.5-9ч, полностью аддитивная, без миграций) — это
  сильный аргумент делать её, когда дойдёт время, а не откладывать бесконечно.
- Она **обнажает** ранее малозаметный дефект поведения при реконнектах
  (зомби-слот из-за задержки хартбита) именно в самом ценном сценарии
  использования (1-на-1) — это не блокер, но требует отдельного внимания при
  реализации, не только «добавить поле и валидацию».
- Она создаёт **новую формулировку риска DoS** («маленький лимит без лобби —
  легче захватить единственный слот»), который нужно явно проговорить
  пользователю в UI и задокументировать в `security.md`, а не молча оставить
  на самотёк.

**Минимально жизнеспособный вариант**, если делать сейчас: только серверная
часть + `<select>` в панели настроек (без отдельной подсказки про DoS-риск и
без специального решения проблемы реконнектов) закрывает 80% ценности за
меньшую часть оценки — но тогда **обязательно** сопроводить документацией
(и, возможно, тултипом в UI) явным «маленький лимит сам по себе не защищает
от захвата слота — используйте вместе с Waiting Room», чтобы не создавать у
пользователей ложного чувства приватности там, где реальную защиту даёт
только лобби.

**Момент**: имеет смысл делать после того, как в проекте появится хоть какой-то
механизм `kick`/`ban` (если он в принципе на дорожной карте) — потому что тогда
же естественно решится и вопрос «лимит ниже текущей занятости» (можно будет
предложить лидеру явно уменьшить состав, а не только блокировать будущих) без
отдельного велосипеда. Если такой фичи не планируется — можно делать
`maxParticipants` уже сейчас как самостоятельную, независимую фичу.
